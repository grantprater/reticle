Comparable Runs

Storing each run's summary and printing the diff, so that a number which moved for the wrong reason cannot arrive looking like a result.

01The summary was the thing that hid the bug

The obvious efficiency move is to make tools print summaries instead of dumps. enemy_detect_eval.py already printed exactly two lines, and it is the tool that produced this, recorded in prototypes/CLAUDE.md:

Already on the record

the aggregate rate is normal (0.42 det/frame against Ascent's 0.40) but the STRONG detections are dominated by purple Ascent foliage and a magenta weapon skin at a fixed screen position (36 of 125 in x 1360-1840, y 320-480). The summary statistic hid this completely; a contact sheet took one glance.

The cheapest possible output was worse than useless: it asserted health while the detector was broken. Cost is not the axis. What separates a useful observation from a misleading one is whether it carries the structure that would falsify it — a count without a concentration measure is not a summary, it is an assertion.

Output shapeTokensWhat it actually tells you
373-row dump high Low — no pattern survives being read one row at a time.
0.42 det/frame ≈ nil Negative — it induced confident wrongness.
Contact sheet, 24 rows mid High — spatial concentration is what a glance is for.
--by-position low High — it carries its own distribution.

02Two kinds of dependency

Comparability is a property of the dependency chain, not of the field. recall keeps its name and its dtype across a class split and stops being the same quantity — the queued ability split is exactly that boundary. So every record declares what it was computed from, in two buckets. Putting a field in the wrong bucket is the only way to get this wrong quietly.

deps · invalidating

Different deps is not a comparison at all. New baseline, and no delta is shown.

  • code fingerprint
  • class list (GLYPH)
  • sampling rule / pool
  • the fit session
  • whether a mask was seeded
context · explanatory

Different context is a comparison, and it is the interesting one. Annotated with what grew.

  • answered label count
  • frames scored
  • rows either side of a fit

Collapse the two and it degrades either way. Everything invalidating and each code touch resets the baseline — the version of this idea that is genuinely useless. Nothing invalidating and you get confident false comparisons across a boundary. Because the label files are append-only, the explanatory case is the common one here: labels arriving is the main legitimate reason a number moves, and it is the case you least want voided.

03The verdict is a total function

Two booleans — did deps move, did context move — with the values either matching or not. That is four outcomes and there are no others, which is why they are a matrix and not a list.

values differ from the baseline
context unchanged context changed
deps unchanged
BROKEN Nothing it depends on moved and the number did. An unversioned edit, or nondeterminism.
CHANGED A real measurement change. Annotated with what grew — this is the case worth reading.
deps changed
INCOMPARABLE A different question. The delta is withheld rather than captioned — printing it with a caveat is the confident-wrongness failure this exists to prevent.
nothing moved
UNCHANGED One line. The common case, and the reason a run costs almost nothing to read.

The BROKEN cell is the derived control. version.py already promises that a version is bumped when a column's meaning changes; read as a contract, that is checkable, and it replaces the standing instruction to confirm a known number by hand.

04Status is not verdict, and it gates the write

A verdict describes a comparison. A status describes the run itself, and only one of the three is ever eligible to be a baseline.

pass The run answered. The only status baseline() will ever return.
cannot-answer The tool refused — no glyph rows, no painted mask. Not a zero, and not a result.
broken A declared external control missed. Everything else in the run is uninterpretable.
Why the gate is the feature

A broken run allowed to become the new normal would re-baseline the fault, and the check would never fire again. That is the seeding mistake in a third costume — after minimap_agent, and after answer() refusing claude-* provenance. So baseline() has no flag to include a non-passing run. The gate is structural, not a convention to remember.

A control is an external truth — checks.KNOWN_KD, a fixture's answer. The tool's own previous output is never one; that is the baseline, and treating it as a control is how a tool ends up scored against itself.

05Deps are fingerprinted, not listed

A hand-kept dependency list rots in the one direction that is silent: add a knob, forget the list, and every later diff crosses a boundary it should have refused. metrics.fingerprint() hashes function source via inspect.getsource plus the named parameters, so the dependency is read off the call rather than remembered.

Granularity is the whole game. Fingerprinting a module would reset the baseline on a comment — the failure mode where this stops being worth having. Fingerprinting the functions that produced the number tracks behaviour and ignores edits elsewhere in the file. Editing a comment inside a fingerprinted function does still reset it. That is the over-declaring side of the trade, taken deliberately: a spurious INCOMPARABLE is visible and cheap; a missed one is silent and expensive.

06What it looks like

$ reticle metrics
dynamic_eval pool/uniform a06f04a0059f: unchanged
dynamic_eval held-out/objects 5822b6646448: CHANGED -- context changed: n_score_rows
    recall                     0.771 ->        0.804
    (n_score_rows now 251)
enemy_detect labels 9acf02f98283: BROKEN -- nothing it depends on
    changed and the numbers did -- an unversioned edit or nondeterminism
    fp                            60 ->           64

A series where nothing moved is one line. That is what makes the tool cheap to read on the ninety-ninth run, and it is the same principle judgement.py arrived at from the other direction: sample where the error rate changes, not where it is high.

07Found while wiring it

The hand-carried control had drifted

CLAUDE.md instructed: confirm a known number comes back — for the detector that is TP 43 / FN 3 / FP 80. The command it was attached to returns TP 42 / FN 4 / FP 60. Nothing had regressed: 43 / 3 / 80 is the unfiltered row of the module's own table (93.5% / 35.0%), while the default run is the shipped configuration (91.3% / 41.2%, matching the docstring exactly). The control had been copied from the wrong row and could not be checked without already knowing which row it came from.

It is the argument for the mechanism, found by building it. The number is no longer written in the conventions; the log holds it, keyed to what produced it.

08Still open

  1. Schema growth is re-baselining in slow motion. Adding a metric is a dep change and comparability resets at that boundary. Correct, and visible rather than silent — but it should be a deliberate act, not a surprise.

  2. No continuous change-point test. judgement.change_point is applied only to the control pass/fail series, which is genuinely binary. A continuous metric needs a different test, and guessing at one would manufacture regimes — the exact failure that test is corrected against.

  3. Nothing records the concentration measures yet. The insight in §1 was that a rate needs a spatial distribution beside it. The mechanism now exists to store one; enemy_detect still records only totals.
